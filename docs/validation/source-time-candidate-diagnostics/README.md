# 源时间度量与 PID 候选诊断

本目录保存已完成的 e381832 正式组和 PID preview=2.5 候选组的**事后只读诊断**。不替代旧正式报告，不修改旧 `legacy_wall` 结论，不改变 1.10 门槛，也不构成终点修复后的真实重跑结果。数据在下一组完整正式矩阵开始之前按已经冻结的 `source_time_trapezoid` 方法复算。

文件为 [diagnostics.json](diagnostics.json) 和 [reproduce.py](reproduce.py)。JSON 记录每个被使用 summary/events 的原始绝对路径与 SHA256、代码 SHA256、两版已核查 frame 契约证据、源时间覆盖、两种 RMSE、配对比例、分段积分、检查点姿态和反事实评分。大体积原始 events 不复制。生成时 `diagnostics.json` 的 SHA256 为 `7d4f297772385d0245bcee075ce45b4b2617a77c6c060a3c00e3f0e856ea87af`。

## 方法和适用边界

源时间窗口包含首次 goal 之前最新的 odom 和随后截至 acquisition_finished 的全部 odom，按接收顺序冻结首条非空全局路径。每个相同源时间戳、相同姿态只保留一次；冲突、回退、非有限或缺失字段不当作有效证据。取唯一观测误差 `e_i`，计算：

```text
E = Σ [(t_(i+1)-t_i) × (e_i² + e_(i+1)²) / 2]
source_time_trapezoid RMSE = sqrt(E / (t_last-t_first))
```

这是误差平方的离散梯形近似，不是连续真实轨迹误差的精确积分或碰撞证明。积分域为实际首末 odom 源时刻，不外推为精确的 goal→acquisition 区间。源间隔及首尾源时间绝对偏移门槛在复算前固定为 0.5 s；可能包含少量 pre-goal 状态或缺少末端少量时间，因此实际 offsets、span、gap 均保留。P95/max 为唯一已观测源姿态的误差分位数/最大值，不是连续时域极值。

`--frame-contract otter_fake_localization` 是针对已核查本项目的显式声明；两版 fake localization 源码和启动日志证实 `otter/map → otter/odom` 恒等，不能凭相同 frame 字符串推定任意项目也成立。新度量降低仿真暂停在墙钟采样中的驻留权重；原 legacy 值同时保留，不能凭新分数抹去原退化。

## 路径末端、航向及完成语义

两次被深入分析的 Python/C++ 首路径前 24 点完全相同，只有末点不同：

| 用例 | 前两个末端点（相同） | Python 旧精确末点 | C++ 格子中心末点 |
| --- | --- | --- | --- |
| straight02 | `(34.25,-10.25)`、`(34.75,-10.25)` | `(35.125,-10.125)` | `(35.25,-10.25)` |
| turn01 | `(23.25,-21.25)`、`(23.25,-21.75)` | `(23.125,-22.125)` | `(23.25,-22.25)` |

straight02 在约 10 m 沿程，Python 的实际航向为 `+0.05535 rad`，最近收到轨迹的名义 2.5 s 预瞄航向约 `+0.05226 rad`；C++ 实际为 `-0.00728 rad`、3 s 轨迹查询约 `-0.00762 rad`。Python 近目标向精确目标所在的较大 y 方向偏转，与末段均值 `y=-10.21092` 对比 C++ `-10.23888` 一致。这支持“末点经 LOS 预瞄影响实际跟踪”的机制，但不能从仅有日志证明它是全部退化原因。

turn01 的差异已在远离终点时出现：约 1 m 沿程，2.5 实际航向 `-1.65753 rad`，2.6 为 `-1.41155 rad`；约 6 m 时分别为 `-1.65302` 和 `-1.57358 rad`。按最近收到轨迹重建的预瞄指向也显示不同的修正相位。JSON 保留检查点和接收年龄；这不是对每次异步控制回调实际引用对象的逐次证明。C++ 的轨迹发布绝对 header 已知错误，因此其相对 3 s 查询不通过该 header 与源时间相减重建。

在被诊断版本中，Python runtime 将 LOS route 末点改为请求精确目标，另用精确目标定义任务完成；控制器进入 1 m 目标圆时若速度仍大于 0.25 m/s，则保持 SETTLING 并零推力，降至门槛内才完成。原 C++ controller 以全局路径末点为目标，位置进入容差即锁存完成，没有该速度条件。此差异根据保留源码核对；C++ 原事件没有 Python navigation_status，不能伪造其状态转换时间。

实际首次进入请求目标 1 m 圆时，Python straight02/turn01 的速度为 0.3004/0.3115 m/s，说明位置进入圆并不等于速度已满足完成条件；采集末端分别为 0.1350/0.1400 m/s、距请求目标 0.6755/0.6915 m。对应 C++ 末端速度为 0.1309/0.1355 m/s、距离 0.5487/0.5082 m。所有尾部实际观测均保留在评分中。

## 只改评分末点的反事实

对同一批 Python 2.5 实测姿态，仅把用于算误差的首路径末点替换为对应 C++ 格子中心：straight02 和 turn01 的**每个已观测误差都完全不变**，最大逐点差为 `0.0 m`，完整源时间 RMSE 也不变。

原因是观测艇位置尚未驶入那条最后短折线的投影区域：straight02 最后 x=34.4512，小于末段起点 x=34.75；turn01 最后 y=-21.4362，尚未越过末段起点 y=-21.75。该反事实只排查“评分路径末点差异直接改变数值”这一机制。它没有改变实际 LOS 预瞄、推进器、惯性或轨迹，**不能代替恢复格子中心引导后的真实重跑，也不能据此改判通过**。

## 复算

在有原始结果的 WSL 中运行，输出必须是尚不存在的文件，且不能位于原始 results 目录之内：

```bash
python3 docs/validation/source-time-candidate-diagnostics/reproduce.py \
  --results-root /home/usv/usv_migration/results \
  --output /tmp/source-time-candidate-diagnostics-recomputed.json
```

脚本仅用 Python 标准库和本仓库已冻结的无 ROS 度量代码。不会启动 ROS/Gazebo、修改原文件或选择新的重复。若未来度量源码发生变化，须先比较 JSON 记录的源 SHA，再解释新的复算结果；不能把不同版本的实现混作同一次已冻结验证。
