# 0211 多必经航点连续航行设计草案

状态：用户已确认，进入实施。用户明确接受1.5m通过半径、转弯与变速时提前减速。基于2026-09-15当前单点导航源码。

## 1. 已确认需求

- 按0211报文`points`数组原始顺序执行；本阶段所有航点均为必经点。
- 中间点连续通过，只在最后一个点正常减速停船。
- `travelId`表示航线编号；每次收到合法0211都是一次新的整条航线执行。
- 航行中收到新的0211，取消旧执行并确认零输出后，从当前位置执行新航线的第一个点。
- 每点`speed`表示驶向该点这一段的期望航速，JSON数值单位为节。例如`speed:4`是4节，即约2.0578m/s。
- 全部航点按顺序经过、最后一点满足到达和低速条件后，才发布一次0052；字段仍为原`travelId`和`taskFinish:1`。

## 2. 本方案采用的初始设置

- 中间点通过半径先取1.5m，与当前单点位置容差一致；设为独立可配置参数。这个值是仿真初始设置，尚未验证在所有转弯、航速下的可达性。
- 终点继续使用当前PID的1.5m位置容差、0.25m/s实际平面速度条件。
- 本阶段接受`taskType:16`、`count`为1至255且与数组长度一致、每个点`type:1`。不在DDS报文添加“必经/非必经”字段。
- 期望航速允许因转弯、加减速距离和避障而降低。连续通过表示中间点不触发常规终点停车；异常或缺少安全路径仍允许停止等待。
- 不自动放宽通过半径或跳过难以到达的点。不能在可用地图中规划到当前必经点时明确报告规划状态。

## 3. 当前实现约束

1. `NavigateTo.srv`只接收一个目标和一个速度。逐个调用该服务会走现有终点减速/停车流程。
2. `controller/controller.py`在真实船位进入`trajectory.goal`圆盘时开始SETTLING并等待低速。中间点必须与最终停车目标区分。
3. `usv_control/control.py`在`task_id`变化时清控制器状态并输出一次零推力。连续切点应保留整条航线的任务生命周期。
4. LOS当前可在预测过程中切换内部几何路点，但该索引不能充当真实艇的必经点完成记录。
5. 路径裁剪、重采样和轨迹生成当前只面向单一导航目标。用户必经点需有独立的顺序/锚点信息，防止被普通路径简化或最近点裁剪跳过。
6. 现有`usv_mission`用于值守等任务且拥有控制输出，本方案沿用当前决策与控制链，不额外启用该控制入口。

## 4. 推荐结构

```text
0211整包
  -> 协议适配：校验全部点、经纬度转ENU、节转m/s
  -> 一次NavigateRoute调用：有序航点、分段速度、整次执行ID
  -> 决策端航线进度：实际确认P1 -> P2 -> ... -> PN
  -> 当前必经点与后续航段的路径、连续LOS轨迹
  -> 现有控制器跟踪；仅最终点启用终点停车判定
  -> 全部完成的导航状态 -> 0052
```

### 4.1 协议与ROS输入

- 在协议适配包中新增纯航线数据模型：航线编号、发送方、有序且不可变的航点列表。一次解析完整报文，格式或字段非法时整包拒绝，不先执行前几个点。
- 新增`RouteWaypoint.msg`，把一个ENU点与该段期望速度放在同一条记录中，避免两条独立数组错位。
- 新增`NavigateRoute.srv`，输入包含整次`request_id`、统一坐标系、有序航点数组；响应沿用接受结果、原因、决策会话和任务编号。
- 保留已有`NavigateTo`和RViz单目标入口。单点0211按长度为1的航线执行，完成行为保持兼容。
- 导航端在接收整条航线时校验所有点的有限值、坐标变换和模型速度上限。几何可通行性需要依据当前及后续地图持续检查，接收成功不等于整条航线必然可达。
- 复用当前内部请求幂等、超时重试、取消确认、旧会话/旧回调隔离逻辑；同一整条航线仅提交一次业务请求。

### 4.2 航线进度归决策端管理

独立纯状态模块保存`execution_id`、航点列表、当前必经点索引和已通过数量。协议适配器不根据绿色预测轨迹推进点序。

- 中间点：用新鲜且时间顺序正确的实测船位判断是否进入通过圆盘；正常连续定位样本的短线段穿过圆盘也可确认，以避免采样恰好跨过小圆盘。
- 定位跳变、时钟重置或不合理的样本间距不能用插值虚构一次通过。
- 一次只按原始点序推进；船离后面的点更近也不改变顺序。
- 相邻同坐标点保留逻辑顺序，到达同一位置可依序满足；不要求无意义的离开再进入。非相邻重复坐标仍须在轮到该索引时确认。
- 仅进入最后一段时，才允许最终点完成判定。航线终点等于出发点、途中提前经过终点坐标时，均不能提前结束。
- `task_id`在整条航线内保持不变；航点切换更新规划版本和进度，旧版本规划结果不得覆盖新进度。

### 4.3 路径与连续轨迹

- A*继续处理障碍绕行。计算到当前必经点的路径，并在地图允许时预先衔接下一段，给连续转弯提供参考。
- 航路点保留为带顺序的锚点。路径简化、重采样和裁剪只处理锚点之间的几何点；精确锚点连接必须通过碰撞检查。
- 为多航点增加明确的连续导引入口，保留已有单点算法路径作为回归基线。
- 预测轨迹可以预演通过后续点，但预测索引与实际已通过索引分开保存。实测未通过当前点时，实际进度不能前移。
- 中间点不使用现有终点的剩余距离减速到零逻辑；转弯速度按可用曲率/偏航角速度限制，并检查完整船体扫掠轨迹。
- 切点本身不清空控制器积分，也不故意输出零推力。新参考准备期间，只能继续使用仍新鲜且安全的已有轨迹；否则按现有安全等待行为处理。
- 下一段尚未获得安全有效参考时，减速或等待，不以盲目前进维持表面连续性。

### 4.4 速度分段与衔接

| 航段 | 期望速度来源 |
|---|---|
| 接收执行时的当前位置 -> P1 | `points[0].speed` |
| P1 -> P2 | `points[1].speed` |
| P2 -> P3 | `points[2].speed` |

速度是期望值，不是要求在边界瞬间跳变的刚性指令。轨迹按模型的加减速度范围构造连续速度剖面；下一段较慢时允许提前减速，转弯时根据可行性降低速度，最后一点准备停车。

若转弯形状、通过半径和速度要求不能同时满足，应报告并减速/等待，不能自行切掉必经点。初版不扩展动态预测时域算法；使用当前配置时长并针对多点场景验证。

### 4.5 中间点与终点参考语义

- 在`NavigationReference`增加明确的中间点通过语义，建议使用`pass_through`：默认false保持单目标终点语义，中间航点为true。
- `goal`携带当前航点位置用于状态和可视化。只有进入最后一点阶段才允许停车/完成。
- ROS参考解码在中间点阶段给控制器提供无终点停车判定的轨迹；仅对有明确通过标志的参考允许这种情况。
- 保留PID/LQR等控制律，修改范围集中在参考语义和进度判断。所有同用导航消息的节点和测试需要同步重新构建。

## 5. 反馈和异常

- 在ROS状态中增加总航点数、当前航点序号、已通过点数、当前段期望速度。显示序号从1开始，并明确区分内部索引。
- 中间点通过只更新进度，不发送0052。
- 最后一点到达且低速后，整条航线仅发送一次0052。
- 中途无路、地图范围不足或航点被障碍占据时，不跳到下一点，不报告整条完成。
- 新0211替换整条旧航线，确认取消后从新报文第一个点开始；不会继承旧航线的点序。
- 旧航线的服务响应、规划结果、控制报告和完成状态不能推进新航线。

## 6. 实施边界与验证

改动集中于协议适配、导航接口、决策航线进度、LOS多点参考及参考编解码。保留当前ROS/DDS域、TCP链路和推进器接口。

实施顺序：

1. 航线解析和纯进度状态机，先验证顺序、容差、重复坐标及非法整包。
2. 整条航线服务与中间/终点参考语义，验证同task_id连续切点和单点兼容。
3. 带必经点约束的路径/轨迹与速度衔接。
4. ROS集成、Gazebo短航路，再由用户工具单次下发完整0211复验。

最低验证矩阵：

- 三个直线航点连续通过，顺序正确，中间无终点停车事件，最后低速完成。
- 三点折线/90度转弯，各点实际最小距离满足通过半径。
- 分段2/4/2节，速度参考平滑衔接，实测航速和跟踪误差另行记录。
- 必经点附近障碍与无法到达场景，不跳点、不虚报完成。
- 闭合航线、提前靠近最终点、相邻重复点和非相邻重复点，不提前完成。
- 原报文重复下发、切点同时收到新航线、取消超时与旧反馈，不串执行进度。
- 单点0211、NavigateTo、RViz入口及现有控制器回归。

验收记录应包括每个点的实际通过时间/距离、点序、速度参考与实测速度、整条航线task_id、终点到达误差和0052次数。ROS夹具到达事件与Gazebo真实航行结果分开报告。
