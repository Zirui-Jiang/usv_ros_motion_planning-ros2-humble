# USV ROS 2 导航仿真工程技术交接

交付日期：2026-09-14。请先阅读本文件，再按根目录 [README.md](README.md) 构建运行。

本包是当前工作目录的完整主线源码快照，适合技术人员阅读、编译、联调和继续开发。包含尚未提交的最新改动，源码及配置逐字节复制，未在打包过程中更改算法。它不是可在 Windows 双击运行的软件安装包。

## 1. 当前实现到什么程度

- 运行环境：Ubuntu 22.04 / WSL2、ROS 2 Humble、Gazebo Classic 11、Python 3 和 C++。
- 普通导航链路：LiDAR 感知与代价地图 → A* 路径规划 → LOS 轨迹生成 → PID 航行控制；可选 Dijkstra、GBFS 和 LQR。
- 感知定位、决策规划、航行控制分别拥有 ROS 节点、launch 和配置入口，共 20 个 ROS 功能包。定位和 TF 当前来自仿真真值。
- 支持目标替换、取消、到点及停稳判定；模块重启后需要重新下发目标。
- `mission_module` 保留值守、圆形巡航及阵位保持代码，普通导航主入口不启动这些任务。
- 当前没有接入 AIS/导航雷达融合、目标跟踪、COLREGs、DWA、MPC；尚未验证真实传感器、实船及跨机部署。

## 4. 首次构建和启动

以下命令在 **Linux / WSL Bash** 中执行，当前目录必须是解压后的工程根目录。建议将工程放到 Linux 文件系统，例如 `~/work/usv_navigation_handover_20260914`，避免长路径及挂载盘性能影响。

先准备 ROS 2 Humble、Gazebo Classic 11、colcon、CMake/C++ 编译器、rosdep，完成 rosdep 初始化。Python 算法依赖主要是 NumPy、PyYAML，测试使用 pytest；ROS 包依赖以各 `package.xml` 为准。

```bash
source /opt/ros/humble/setup.bash
rosdep install --from-paths src --ignore-src --rosdistro humble -r -y
colcon build --base-paths src --executor sequential \
  --cmake-args -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
source install/setup.bash
ros2 launch sim_env main.launch.py world:=ocean headless:=true
```

依赖安装成功后再构建。修改源码中的 YAML、world 或模型资源后重新构建，使安装区与源码一致。每个新终端都要先加载 `/opt/ros/humble/setup.bash` 和本工程 `install/setup.bash`。

如果需要 Gazebo 和 RViz 界面，先停止前一实例，再执行：

```bash
source /usr/share/gazebo/setup.sh
ros2 launch sim_env main.launch.py world:=ocean
```

需要可用的桌面 / WSLg。首次启动推荐直接使用上述 `ros2 launch` 命令；原有 `scripts/main.sh` 还会尝试根据 `src/user_config/user_config.yaml` 生成场景障碍。

在另一个已加载环境的终端，等待仿真、定位和代价地图就绪后下发目标：

```bash
ros2 topic pub --once /otter/goal geometry_msgs/msg/PoseStamped \
  '{header: {frame_id: otter/map}, pose: {position: {x: 35.0, y: -10.0, z: 0.0}, orientation: {w: 1.0}}}'
ros2 topic echo /otter/navigation_status
```

上述坐标来自工程默认 `ocean` 示例，调整场景后需确认目标在可通行水面。取消目标：

```bash
ros2 service call /otter/cancel_navigation std_srvs/srv/Trigger '{}'
```

取消成功代表控制端已确认零输出，船体可能继续滑行；导航完成另外要求位置和速度满足判据。

## 5. 分模块接手与接口定位

| 职责 | 优先查看的实现 | 配置或接口 |
| --- | --- | --- |
| 感知与建图 | `src/core/perception_module/perception/perception/mapping.py`、`usv_perception/usv_perception/mapping_node.py`、`usv_perception/src/costmap_support_node.cpp` | `src/core/perception_module/usv_perception/config/` |
| 决策与任务调度 | `src/core/decision_module/usv_decision/usv_decision/decision.py`、`runtime.py` | `src/core/shared/usv_navigation/` 提供配置和协议支持 |
| 路径搜索 | `src/core/decision_module/path_planner/path_planner/` | `shared/usv_navigation/config/path_planner/` |
| 轨迹生成 | `src/core/decision_module/trajectory_planner/trajectory_planner/` | `shared/usv_navigation/config/trajectory_planner/` |
| 航控调度与 PID/LQR | `src/core/control_module/usv_control/usv_control/control.py`、`controller/controller/` | `shared/usv_navigation/config/robots/otter/controller_params_otter.yaml` |
| 船舶模型、状态及数值接口 | `src/core/shared/common/common/` | `shared/usv_navigation/config/robots/otter/dynamics_otter.yaml` |
| 模块间 ROS 消息 | `src/core/shared/usv_navigation_interfaces/msg/` | `NavigationReference`、`TrajectoryPoint`、`ControlReport`、`ModuleHeartbeat` |
| 仿真组合与资源 | `src/sim_env/launch/`、`worlds/`、`models/`、`urdf/` | Gazebo / RViz 插件在 `src/plugins/` |

表格中的 `shared/...` 相对 `src/core/`；同一单元格中的简写目录相对所属业务模块。

核心数据流：自船 `odom/TF` 和感知 `costmap_raw` 进入决策与航控；决策发布 `navigation/reference` 完整轨迹；航控发布推进器命令并经 `navigation/control_report` 返回执行状态。`global_path`、`local_trajectory` 是显示接口，不能代替完整执行轨迹。

纯算法层常用契约为 `compute(state, trajectory, dt) -> ControlCommand`；状态、轨迹的时间与坐标系必须一致。`left/right` 是归一化推进器命令，不能直接当作牛顿或 PWM。控制器实例在周期之间保留内部状态，具体重置边界由现有调度实现定义。

需要分别联调时，在四个终端分别运行：

```bash
ros2 launch sim_env simulation_support.launch.py world:=ocean headless:=true
ros2 launch usv_perception perception.launch.py
ros2 launch usv_decision decision.launch.py
ros2 launch usv_control control.launch.py
```

这些入口已由 `main.launch.py` 组合，分模块启动时不要同时运行完整主入口。所有终端保持命名空间、ROS domain 和配置一致。
