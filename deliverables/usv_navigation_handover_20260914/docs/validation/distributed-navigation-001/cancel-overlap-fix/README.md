# 重叠取消请求的反馈修复验证

日期：2026-09-13。

本次只修复拆分后新增的取消 ACK 匹配边界。决策节点先验证航控和规划会话，再使用实际收到的报告匹配各个待取消请求，最后按当前任务编号筛选用于任务状态、完成和参考撤销的报告。旧任务报告不会覆盖当前任务或其报告缓存。

取消成功条件保持为：实际收到同一取消任务的报告、报告参考序号不小于取消命令序号、左右及横向三路推力均为零。不将较新任务的 ACK 视为较早取消的 ACK，不缓存或推断缺失的 ACK；无匹配报告仍按原有 2 秒期限返回失败。

验证使用真实 `DecisionNode`、`ControlNode`、ROS 2 话题及服务和模拟传感器输入。节点由同一个单线程 executor 调度；测试通过临时移除航控节点，使取消与替换请求先进入决策节点，再恢复航控调度。没有启动 Gazebo，没有修改安装区。本记录不替代独立进程或 Gazebo 验证。

| 阶段 | 执行范围 | 结果 |
| --- | --- | --- |
| RED | 3 个新增测试，决策实现尚未修改 | 2 failed、1 passed、5 deselected，12.30 秒 |
| GREEN | 完整 `test_distributed_ros.py`，包含原 5 项与新增 3 项 | 8 passed，17.75 秒；命令退出码 0 |

RED 中两个失败用例都先断言收到了对应取消任务的真实零推力报告，再因取消响应 `success=False` 而失败。因此失败原因是 ACK 被当前任务过滤条件丢弃，不是航控没有发送 ACK。无任何航控 ACK 的负例在 RED 和 GREEN 中均保持超时失败。

新增覆盖：

1. 航控暂不调度时连续发送两次取消，恢复后各自匹配实际零输出确认。
2. 取消等待期间替换目标；较早任务的实际零 ACK 完成取消请求，但不改变新任务编号、目标、状态、参考或当前报告缓存；新任务随后继续产生推进输出。
3. 取消后替换目标，但始终不恢复航控调度；没有实际 ACK，取消响应必须失败，新目标仍保留。

完整命令见 `red-command.txt` 和 `green-command.txt`，pytest 原始输出见 `red.log` 和 `green.log`。首轮 RED 的 shell 包装命令在转发退出码时另外出现 `exit: : numeric argument required`；该警告发生在 pytest 完成并保存日志之后，未影响两个测试失败的证据。GREEN 使用 `pipefail` 与 `tee` 正确保留退出码。

由于本次新增包尚未加入 Git 索引，普通 `git diff --check -- <文件>` 不检查其内容；额外用 `git diff --no-index --check -- /dev/null <文件>` 检查两个源码文件。两次检查均无空白错误输出；`--no-index` 比较非空文件与 `/dev/null` 的退出码为 1，表示存在文件差异。结果和源码 SHA-256 见 `source-checks.json`。
